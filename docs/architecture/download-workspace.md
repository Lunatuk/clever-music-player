# Общий рабочий бюджет загрузки

Пакет 44, 18 октября 2026. Внутренний desktop pipeline; обычный запуск и экран
Яндекса пока не открывают эту область. Схема БД 13 и зависимости прежние.

## Учёт и владение

DownloadWorkspace открывается явно в существующем app-private parent и создаёт
только `.cmp-download-workspace-v1`. Корень имеет точный owner marker, постоянный
owner.lock и operations. NativePublicationFiles удерживает OS lock до завершения
всех принятых читателей. Другой процесс или алиас того же физического пути не
может открыть область. Возраст файлов, PID и истечение download lease не
используются для предположения, что файл больше никто не читает.

Один и тот же экземпляр передаётся RawDownloadPool, MetadataPreparer и
DesktopDownloadCoordinator/PublicationStore. Препарер и координатор отвергают
разные бюджеты. Будущий composition root обязан связать с ним и транспорт;
передача произвольного FileAudioSource сама по себе этого не доказывает.
Прежние низкоуровневые конструкторы без workspace сохранены для совместимости;
они не объявляются участниками общего бюджета.

По умолчанию резервируются до 2 GiB данных и 128 записей. Максимальные настройки
64 GiB/512; файл до 8 GiB, обложка до 8 MiB. Журнал ограничен отдельно: запись
до 32 KiB, то есть до 4 MiB при стандартном количестве, плюс фиксированные
owner/lock файлы. Резерв считается целиком до выдачи первых байтов и не зависит
от фактического заполнения файла. Это общий допуск операций, не OS disk quota,
не проверка свободного места на каждом диске и не лимит готовой фонотеки.

Raw резервируется синхронно до binary HTTP; разные raw pools разделяют счётчик.
Подготовка резервирует source size + 32 MiB (настраивается, максимум 8 GiB) и
размер поставленной обложки до дорогого хэширования/запуска helper. Публикация
резервирует проверенный размер следующей копии до создания своего audio.part.
Одновременные raw/prepared/publication действительно учитываются вместе;
слишком маленький бюджет явно прерывает операцию, а не переходит на другой
неучтённый временный каталог. Смена стадии сама по себе не освобождает данные,
которые продолжает читать следующий компонент.

Каждый резерв получает случайный ID и неизменяемый canonical JSON. Запись
reservation.part flush-ится и переносится без перезаписи в reservation.json
до payload. Raw/prepared данные располагаются в этой же плоской области:
audio.part и, при наличии, cover.part. Credentials, URL и названия треков не
сохраняются. Publication reference содержит только канонический destination
root и проверенное имя operation; этот приватный путь не входит в диагностику.
Неполученный/нулевой размер HTTP не уменьшает резерв автоматически.

## Предел подготовки

Управляемый preparer передаёт свой предел backend, и FFmpeg получает его через
`-fs`; после завершения размер проверяется ещё раз. Результат сверх предела не
доходит до проверки/импорта. Полное декодирование, сравнение packets/PCM/обложки,
хэш исходника и проверка длительности остаются обязательными: остановившийся
по размеру helper не превращает обрезанную песню в успешную загрузку.

FFmpeg прямо допускает небольшое превышение `-fs` при записи пакета/контейнера:
[официальная документация](https://ffmpeg.org/ffmpeg.html#Main-options).
Поэтому резервирование не объявляется жёстким потолком мгновенного физического
размера стороннего процесса. Такой выход отклоняется и очищается; ОС-квоты или
ограниченный seekable output adapter — отдельная задача, если понадобится
строгая гарантия пикового дискового потребления. Проверены реальные MP3/M4A/FLAC
и отказ при недостаточном бюджете для тегов/обложки, без перекодирования аудио.

## Восстановление и очистка

При явном open или recover, под эксклюзивным корневым lock, область просматривает
только свои operations. Не более 4096 имён за проход; JSON читается ограниченно.
Живые резервы текущего владельца пропускаются, включая уже выданный raw/prepared
файл. Закрытие workspace прекращает допуск и ждёт их close, затем дренирует
файловые операции и освобождает lock. Старый cleanup не может начать работу
после закрытия или после открытия новым владельцем.

Согласованные брошенные raw/prepared файлы удаляются вместе с их записью,
marker удаляется последним. Удаляются только известные обычные файлы и пустой
каталог; рекурсивного удаления нет. Полная reservation.part после прерванной
установки и пустой каталог после удаления последнего marker восстанавливаются.
Неизвестные файлы/вложенные каталоги/ссылки/неверный ID, версия, размер или JSON
сохраняются. Они блокируют новый допуск до явного разбора и успешного recover.
Частично записанный недоказуемый marker не угадывается по одному имени.
Старые cmp_raw_download_*/cmp_audio_metadata_* вне новой области не удаляются.

Ошибка удаления не освобождает резерв фиктивно. Можно повторить cleanup; после
закрытия владельца разбор выполняет следующий экземпляр. Неудачный/отменённый
проход восстановления оставляет допуск закрытым до полного повторного прохода.
Поздняя отмена первого open дренирует создание owner marker и operations;
последующий повтор получает полностью инициализированный корень.

Publication payload остаётся в прежней папке/журнале публикации. Рабочая область
его не удаляет: хранит свой резерв, освобождает собственный metadata marker
только после наблюдения отсутствия audio.part под прежним OS resource lock.
Занятый lock, недоступный/изменённый destination, неизвестный журнал или всё ещё
существующая копия сохраняют резерв и после повторного open. Удаление самой
копии разрешает прежняя DB-fenced PublicationRetention, затем workspace.recover
освобождает общий резерв. Готовая перемещённая музыка, в том числе ожидающая
импорта/reconciliation, не удаляется и не считается временной копией. Прежняя
publication quota и её retention journal дополнительно сохраняют свой учёт.

## Проверки и границы

Проверены совместный допуск, reader lifetime, root aliases/другой процесс,
нештатный exit без cleanup, отказ Windows delete, повторная очистка, повреждённые
markers, запрет устаревшего cleanup, отмена восстановления, потеря destination,
занятый внешний lock и очистка publication только через прежнюю DB authority.
Subprocess writer использует production C lock и точные записи, предварительно
сериализованные DownloadWorkspace; восстановление выполняет настоящий сервис.
Это проверка завершения процесса после flush, не симуляция отключения питания.

Native lock adapter квалифицирован здесь на Windows; Android app-private lock
и SAF publication/теги, macOS helper ещё требуют платформенных проверок.
Приватная область и native locks не являются sandbox от намеренной внешней
подмены всего дерева; directory fsync/power-loss гарантии не добавлены.
Скачивание реального аккаунта/обложек и UI runner пока не включены.
Следом — ограниченное получение обложки, затем session-bound runner с кнопкой,
прогрессом, отменой и проверкой маленькой реальной коллекции.

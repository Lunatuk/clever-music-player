# Desktop staging и публикация, пакет 31

`DesktopPublicationStore` — внутренний владелец рабочей области. `run` получает
актуальный выполняющийся DownloadJob, открывает сохранённое назначение через
репозиторий, берёт OS-блокировку и передаёт `PublicationWorkspace` callback.
Автоматического запуска, записи в пользовательские папки при старте, UI,
сетевого исполнителя или импорта Track нет. Схема остаётся 13.

## Рабочая область

В назначении создаётся `.cmp-publications-v1` с фиксированным owner.json,
locks и operations. Чужой каталог без корректного маркера не присваивается.
Компоненты проверяются как каталоги/файлы без следования символическим ссылкам;
корень разрешается в канонический путь. Это управляемая область приложения,
не OS sandbox против враждебной замены дерева между syscalls. Другой процесс
не должен менять/перемещать её во время работы. Проверки связей не заменяют
будущую политику доступа/разрешений Android SAF.

Resource key — SHA-256 канонической тройки provider/ID/variantKey. Quality,
account и ID записи папки не включаются: разные качества, сессии и алиасы одной
физической папки сериализуются по одному файлу блокировки. Версии различаются.
Постоянный lock-файл не удаляется: удаление могло бы создать два независимых
объекта блокировки для одного ключа. Занятое назначение даёт busy, без ожидания
и неограниченной очереди. Будущий runner должен повторять захват в той же
попытке с продлением lease, а не расходовать новые попытки в цикле.

Уникальный publicationId — 256 случайных бит. Operations имеет подкаталог
resourceKey-publicationId; входные ID/названия не становятся компонентами пути.
`writeAudio` создаёт только audio.part, принимает поток с точным ожидаемым
размером до 8 ГиБ, ограничивает один write 256 КиБ, проверяет байты/переполнение/
короткое чтение, прекращает 16 пустых chunk подряд, flush/close writer перед
возвратом. Сканер не принимает расширение .part. После записи будущий помощник
может добавить теги/обложку и должен полностью закрыть свои writers/processes
перед валидатором пакета 30 и publish. Размер доказательства относится к готовому
файлу после тегов, исходный размер HTTP проверяется writeAudio отдельно.

## Владение и файловый эффект

`DownloadJobRepository.withOwnedDestination` сначала выполняет no-op UPDATE
в SQLite-транзакции, получая writer reservation, затем читает полный CAS-снимок,
активную сессию и включённую папку. Clock проверяется после reservation и ещё
раз непосредственно перед callback: время, выбранное до ожидания lock, не
позволяет старой lease пройти проверку. Job/revision не меняются.

Транзакция допускает только короткий физический эффект/подготовку области.
Внутри запрещены сеть, hash/decode, ожидание другого подключения и длинная
внешняя транзакция. OS-lock захватывается без блокирующего ожидания, поэтому
порядок SQLite/OS-lock не образует взаимного ожидания. Hash/декодер работают вне
SQLite. Второй writer/смена аккаунта/папки/claim не проходят до завершения
принятого эффекта. Lease может истечь во время syscall, но новый DB-владелец
в этой точке ещё не принимается. Это порядок операций, не транзакция ОС+SQLite:
сбой/rollback после эффекта требует журнала и reconciliation.

Publish требует running/publication, тот же job/key/account/session/attempt
token, доказательство фактического качества и времени текущей попытки.
Старая workspace не перепривязывается к следующему token. Staging защищается
read seal, полностью хэшируется, сравнивается с доказательством пакета 30.
Сначала записывается immutable intent.json через уникальный .part + flush и
публикацию без замены. Затем под новой DB-fence проверяется каноническое
назначение и выполняется один перенос. Готовое имя cmp-resourceKey-publicationId
имеет проверенное расширение mp3/m4a/flac; теги/отображаемые названия от него
не зависят. Совпавшее чужое имя, даже с одинаковыми байтами, не перезаписывается.

На Windows используется MoveFileExW без REPLACE_EXISTING/COPY_ALLOWED, с
WRITE_THROUGH. Никакого copy fallback на другой том. Read seal через CreateFileW
разрешает READ/DELETE и исключает новые/уже открытые write handles; OS-lock
назначения использует share mode 0. Unicode/extended paths поддержаны.
[MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).

На macOS/Linux используется flock(LOCK_EX|LOCK_NB), open с NOFOLLOW/CLOEXEC,
и link→unlink на одной FS: имя создаётся атомарно, EEXIST ничего не заменяет.
Сбой между link/unlink оставляет две ссылки на один inode. Эти блокировки
advisory: сторонний writer, не соблюдающий контракт, не защищён ими.
[Apple flock](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html),
[Apple link](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/link.2.html).
Физический прогон macOS/Linux здесь не выполнен; отсутствие поддержки FS
возвращает отказ, небезопасного fallback нет. Для Android нужен отдельный SAF
publish/журнал, desktop API на телефоне не используется.

## Журнал и восстановление

После принятого переноса выполняется полный hash итогового файла и immutable
published.json. Отмена после принятия дренирует этот путь и сообщает настоящий
результат, а не «отменено без изменений». Ошибка после возможного эффекта даёт
needsReconciliation; файлы не удаляются. Коллизия на самой OS-границе тоже
сверяется отдельно, ничего не подменяет. Положительный PublicationReceipt
означает файловую публикацию, не completed задания или импорт в SQLite.

`reconcile` вызывается явно с publicationId в новой актуальной workspace.
Канонический JSON ограничен 16 КиБ, фиксированы версия/ключи/типы/границы,
пути вычисляются заново, а не читаются из JSON. Сверяются job/key/ID, итоговый
SHA-256/размер, marker. Если staging остался, он должен быть тем же inode,
совпадения содержимого недостаточно. Отсутствие готового файла не превращает
intent/неполный staging в успех и не вызывает слепое копирование. Обнаруженный
результат получает свежее время проверки, прежние свойства аудио подтверждаются
через полное совпадение байтов. Старый marker не переписывается.

pendingPublications возвращает immutable список явных intent для текущего
job/key. Пределы: 10 000 просмотренных entries / 256 записей одного ключа,
превышение — ошибка без усечения. Автоудаление временных файлов/старых receipt
ещё не включено: до публичного downloader нужны retention, квота и очистка
после подтверждённого импорта. Ни старые версии музыки, ни чужие файлы этот
модуль не удаляет. Flush/атомарные имена покрывают ошибки процесса; без directory
fsync/испытаний питания не заявляется полная устойчивость к потере питания.

## Нативный мост и жизненный цикл

`cmp_file_ops` — небольшой локальный C code asset через имеющиеся hooks/code_assets/
native_toolchain_c, без обновления прежних hosted-зависимостей. C захватывает
GetLastError/errno до возврата в VM и возвращает числовой код. Прямое чтение
GetLastError отдельным Dart FFI-вызовом воспроизвело код 0 вместо ошибки;
eager lookup не устраняет проблему атомарности перехода VM.
[Ограничение Dart FFI](https://github.com/dart-lang/sdk/issues/38832).
Мост входит в native assets установленного плеера, внешнего компилятора при
запуске не требует. На Android сборка также проверяет 16 КиБ alignment.

Один store принимает одну workspace; одна workspace — одну операцию.
close закрывает приём, отменяет stream и дренирует writer/hash/принятый effect,
затем освобождает OS-lock. Даже забытая вызывающим Future остаётся собственностью
workspace и дренируется перед её закрытием. Ошибка admission commit после
создания workspace также освобождает lock. Native syscalls выполняются в worker;
жёсткий timeout зависшего ОС-вызова/чужого callback не обещается.
Будущий координатор обязан закрыть store до SQLite, как остальные владельцы.

Тесты: временные файлы/SQLite, два независимых подключения, два OS-процесса,
ошибки до/после переноса и receipt, обычные/racing коллизии, изменение байтов,
отмена stream/после эффекта, release после crash владельца, длинные пути,
старые lease/token, marker/JSON, незавершённые и забытые операции. Дочерний
процесс напрямую загружает уже построенный C asset: отдельная компиляция
помощника не подменяет межпроцессную проверку.

В desktop CI тестовый native_assets.json архивируется перед release, DLL
сохраняются. Тестовая карта с абсолютными путями не должна попадать в продукт.
Самостоятельный FFmpeg/native downloader bundle, теги/обложки, координатор,
импорт и вход/кнопка обновления остаются следующими шагами.

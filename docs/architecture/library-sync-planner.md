# Планировщик обновления библиотеки, пакет 28

LibrarySyncPlanner — чистая функция общего доменного слоя. Она сравнивает
сохранённые выбранные коллекции, кандидаты локальных ресурсов и очередь,
возвращая проверяемый LibrarySyncPlan. Сеть, чтение файлов, рекомендации,
вход в аккаунт и новые кнопки пока не подключаются.

## Согласованный вход

AppRepositories.librarySync.capture читает актуальный активный аккаунт,
назначение, все выбранные коллекции и их последний успешный состав в одной
транзакции SQLite. Несуществующий аккаунт/назначение или сменившаяся сессия
возвращают null. Папка фиксируется по ID, адресу и isEnabled; время сканирования
не влияет на план. Входные списки и выходной план — неизменяемые копии.

Неполученная выбранная коллекция блокирует весь план, включая отмену старых
заданий. minimumCompletedAt позволяет координатору потребовать свежий успешный
снимок каждой выбранной коллекции, например после начала текущего обновления.
Без cutoff допускается план по сохранённому полному составу: он не обещает
свежие данные сервиса. Ошибка/частичный ответ не выдаётся за пустой список.
Выключенная папка и неактивный аккаунт также блокируют план.

Максимум 256 выбранных коллекций и 100 000 суммарных позиций; превышение явно
отклоняется, без усечения. Кандидаты ресурсов и задания читаются ограниченными
запросами по назначению, не отдельным SQL на каждую песню. Bulk lookup ресурсов
использует те же правила, что точный findCandidates: фактическое качество,
verified, текущий адрес/известные размер/hash, непропавший Track и включённый
источник. До 100 000 строк за такой lookup; при превышении — явная ошибка.

## Решения по трекам

Точные provider/ID/variantKey объединяются между списками; название и имя файла
не участвуют. Для каждой уникальной песни сохраняются ID исходных коллекций
и число вхождений. Порядок первых появлений стабилен; полный порядок и повторные
позиции по-прежнему находятся в удалённых снимках. Версии, регистр и ведущие
нули сохраняются. Ключ задания включает точное назначение и requested quality.

| Решение | Значение |
| --- | --- |
| joinJob | Есть незавершённое задание текущей сессии; присоединиться, не создавать работу и не сбрасывать бюджет |
| checkExisting | Есть подходящий кандидат БД; выполнить физическую проверку перед повторным использованием |
| createJob | Нет подходящего кандидата и задания; поставить одно задание |
| repairCompleted | Completed больше не имеет подходящего доказательства; явно запросить reconciliation прежнего задания |
| retryJob | Failed/cancelled при явно включённом retryTerminalJobs; пополнить конечный бюджет и пройти reconciliation |
| needsAction | Terminal без разрешения повтора либо незавершённое задание другой сессии; не перепривязывать молча |

Незавершённое задание имеет приоритет над кандидатом, чтобы не обходить уже
запрошенную работу. Проверяемые кандидаты не считаются «уже скачано» только по
записи SQLite; apply не подтверждает их и не читает файл. Будущий координатор
должен проверить ОС/содержимое, обновить DownloadedAsset через CAS и при изменении
состояния построить новый план. Качество сравнивается точно по actualQuality,
без неявного повышения/понижения или вывода из расширения.

## Лишняя работа и повторные команды

Все выбранные коллекции образуют полный желаемый состав для назначения/качества.
Не нужные ему незавершённые задания текущего аккаунта/сессии отменяются, включая
устаревшее качество. Общий трек остаётся нужным, пока входит хотя бы в один список.
Явно пустой выбор отменяет pending work этого назначения. Другая папка/провайдер/
сессия и terminal history не затрагиваются. Локальные файлы, лайки, история,
плейлисты и удалённые снимки не удаляются и не переписываются.

Повторное обновление обычно joinJob/checkExisting. По умолчанию failed/cancelled
не получают новый бюджет на каждом нажатии; нужен явный retryTerminalJobs.
Смена аккаунта может перепривязать отменённое задание только с таким разрешением,
для песни в выбранных списках нового аккаунта. Repair completed никогда не
означает слепую повторную загрузку: сохраняется этап и обязательная сверка файлов.

## Атомарное применение

librarySync.apply повторно читает полный вход в транзакции и сравнивает снимки,
затем заново выводит канонический план. Изменение выбора/состава/сессии/адреса/
доступности кандидата/очереди или подмена команд дают stale без частичных изменений.
Blocked план даёт blocked. Изменение местного лайка или одного времени сканирования
не делает план устаревшим. Ни один из статусов не означает завершение сетевой
синхронизации: applied означает лишь принятие изменений очереди.

Отмена лишней работы, постановка блоками до 64 и retry/repair находятся в одной
внешней транзакции. Ошибка позднего блока откатывает предыдущие вставки и отмену
попыток. Поздний отказ CAS также откатывает уже созданные задания и возвращает stale.
Результат содержит неизменяемые scheduledJobs/cancelledJobs. SQLite busy/прочие
ошибки не маскируются успехом; будущий координатор ограниченно повторяет capture/plan
после изменения данных и не держит транзакцию во время сети или файловых проверок.

Схема остаётся 13, новые таблицы не нужны. Bootstrap не запускает синхронизацию
автоматически. Сетевой адаптер, verifier, staging/receipts/публикация, координатор,
фоновые платформенные работы и UI остаются следующими этапами. Тесты покрывают
чистые решения, 10 000 треков, границы, stale/rollback, общие списки, смену качества/
аккаунта, независимые назначения/провайдеры, сохранность данных и file-backed reopen.

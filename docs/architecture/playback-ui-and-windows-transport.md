# Панели воспроизведения и Windows-транспорт

13 октября 2026 года, пакет 7. Начало разделения UI по этапу 2; Android-прототип и модель системных URI остаются отдельными задачами.

## Границы компонентов

| Компонент | Ответственность |
| --- | --- |
| `BottomPlayerBar` | Текущий трек, прогресс, управление транспортом и действиями; получает существующие сервисы и поток библиотеки |
| `PlayerVolumeControl` | Громкость/mute и всплывающий регулятор в узком окне; не создаёт аудиоплеер |
| `QueuePanel` | Отображение ручной очереди и вызов переданных обработчиков |
| `TrackFeedbackIconButton` | Общий вид кнопок оценки в списке и плеере |
| `track_display_helpers.dart` | Прежние правила подписей и сравнения ID/пути, общие для панелей |
| `HomeScreen` | Навигация, потоки медиатеки, пока ещё страницы и операции библиотеки |

Перенос сохраняет прежние обработчики, строки, ключи виджетов, размеры, состояния и жизненный цикл overlay. Панели не открывают БД, не выбирают платформу и не создают независимую очередь/декодеры. Новые публичные виджеты принимают ключи Flutter.

`AppDependencies` по-прежнему предоставляет один логический `PlayerService` (`TransitionPlayerService` с двумя декодерами) и один `PlaybackQueueService`. Play/pause/seek/volume идут в общий плеер; next/previous, контекст списка и оценки — в общую очередь. Автоподготовка и переходы координируются этими сервисами. Windows/macOS-медиакнопки используют те же экземпляры. Android-сервис позднее должен подключаться к этой сессии; текущий перенос панелей сам по себе фонового Android-аудио не добавляет.

## Причина первого Play

В установленном `just_audio 0.10.5` `play()` сначала устанавливает желаемый `playing=true`, затем асинхронно активирует аудиосессию. До нативного вызова библиотека повторно проверяет `playing`.

WinRT при открытии источника сообщает Opening/Buffering/Paused. Прежний Windows-адаптер переводил любое состояние, кроме Playing, в `PlayerData.playing=false`. Позднее сообщение подготовки могло отменить первый `play()` во время активации сессии: файл уже открыт, но вызова `MediaPlayer.Play` ещё нет. Второе нажатие работало после завершённой активации.

Теперь native player-data содержит только настройки громкости, скорости, повтора и shuffle. Processing state и timeline продолжают приходить отдельным каналом playback-events. Желаемым транспортом управляет `just_audio`; явная пауза из UI/системной медиакнопки проходит через общий Dart-плеер. Нативные SMTC/CommandManager этого декодера отключены ранее, системными кнопками управляет отдельный сервис приложения. Если позже WinRT получит самостоятельные внешние транспортные команды, для них потребуется отдельная согласованная обработка; зеркалировать любое временное состояние открытия в команду паузы нельзя.

Это исправление протокола Windows; повторных Play, таймеров автозапуска и изменений алгоритма очереди не добавлено.

## Проверка контракта

`player_data.hpp` формирует данные и для настоящего Windows-плагина, и для `tool/windows_player_data_fixture.cpp`. PowerShell-команда компилирует формирователь MSVC с заголовками установленного Flutter и сравнивает результат с фиксированным JSON в `test/fixtures`. Обычный запуск команды проверяет соответствие; `-UpdateFixture` используется только при намеренном изменении контракта.

Flutter-регрессия использует настоящий `JustAudioEngine` и установленную библиотеку `just_audio` с управляемыми method/event channels. Активация первой аудиосессии удерживается до доставки сообщения подготовки из нативной фикстуры. До исправления нативных Play-вызовов было 0 вместо 1; после исправления один запрос доходит, последующие pause/resume/stop работают. Windows CI проверяет нативную фикстуру перед общими тестами.

Журнал дополнен запросами Play/Pause и наблюдаемыми изменениями состояния. Эти события помогают отличить подготовку от команды запуска; они не измеряют физический выход звука.

Проверки каналов не заменяют WinRT/акустические испытания. Первый реальный звук после холодного старта, плавный переход и доступные медиакнопки проверяются по короткому чек-листу пакета 7. Android и macOS в этой среде не запускались.


## Пакет 8: владение операциями медиатеки

`AppDependencies` создаёт один `LibraryController` с адаптером выбора папки,
сканером и `LibraryManagementService`. UI хранит только навигацию и отображение;
состояние сканирования, результат/ошибка и допуск операций принадлежат контроллеру.
`HomeScreen` подписывается в `didChangeDependencies`, отписывается при замене
зависимостей/закрытии и не уничтожает контроллер вместе со страницей.

Резервирование происходит синхронно перед первым await, включая выбор папки.
Одновременно допускается одна команда добавления, пересканирования, изменения
флага enabled или удаления источника. Конкурирующие вызовы возвращают `busy`,
а не ставят устаревшее действие в очередь. Выбор папки/изменение источника и
непосредственное сканирование — разные фазы, поэтому UI блокирует действия
на всей операции, а статус сканирования показывает только настоящий обход.
Воспроизведение использует прежние сервисы и не блокируется этим контроллером.

Пятёрка кодов поля диагностики `libraryOperation`: 1 — добавление папки,
2 — общее пересканирование, 3 — одна папка, 4 — enabled, 5 — удаление.
Записываются начало, завершение и ошибка без пути или текста исключения.

`close()` прекращает приём новых команд. Результат ещё открытого внешнего
picker игнорируется; ждать его для закрытия БД не требуется. Уже начатая работа
с БД дренируется. `AppDependencies.dispose()` закрывает допуск сразу, затем
завершает сервисы/активную работу и закрывает SQLite. Поздние результаты не
уведомляют закрытые подписки. Принудительное завершение процесса может оборвать
сканирование: оно остаётся инкрементальной работой, а не общей транзакцией всей
медиатеки. Отмена/прогресс обхода остаются отдельной задачей.

`LibraryFolderRemovalRepository` задаёт обязательный атомарный контракт удаления.
Drift проверяет актуальный enabled внутри транзакции, удаляет связанные записи
и сам источник, проверяет фактическое удаление одной строки. Ошибка/игнорирование
DELETE откатывает весь набор; повтор после уже завершённого удаления безопасен.
`LibraryManagementService` не имеет опасного запасного пути из двух независимых
удалений. Источники на диске не затрагиваются, схема 9 не меняется.

Контроллер координирует команды текущего экземпляра приложения. Низкоуровневые
репозитории/сканер сами по себе не становятся общим межпроцессным планировщиком.
Будущие загрузки, URI-адаптеры и Android-фон должны подключаться к общему
координатору; этот блок не объявляет их реализованными.

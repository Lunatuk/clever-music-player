# Полнота метаданных и предпочтительный вариант файла

Уточнение требований после проверки 0.4.1. Шаг 1 реализован в 0.8.0+2073,
шаг 2 в 0.9.0+2074. Сопоставление локальной копии перед загрузкой работает с 0.10.0+2075.
Повторный Android-импорт проверен на телефоне в 0.7.1: 210,399/199,823 с,
полный пакетный охват, без fallback/stale/ошибок. Блок метаданных начат.
Этот блок выполняется перед автоматическим выбором/пропуском вариантов загрузки.

## Наблюдение и подтверждённые причины

На примере Andromeda / ANDROMEDA старый M4A содержит альбом, исполнителя альбома,
год, жанр, номер и ссылку источника; новый — меньше сведений. Окна свойств
показывают 194 кбит/с у обоих файлов. Совпадение названия/длительности/битрейта
само по себе не устанавливает идентичность записи или релиза.

Текущее metadataConfidence не измеряет полноту и не является калиброванной
вероятностью правильности:

- mergeMetadata даёт 0.95 при полезных названии и исполнителе из тегов.
- До 0.8.0 EmbeddedAudioMetadataReaderService и AndroidPublishedTrackReader
  ставили 1 для пути проверенной загрузки, включая неполные теги.
- До 0.8.0 интерфейс показывал одно и то же «теги 0.95/1.00», создавая ложное впечатление
  сравнимой оценки файлов. Изменение пути импорта не должно повышать оценку
  одного и того же набора сведений.

Дополнительно YandexDownloadProtocol читает album/album_artist/genre/date/track/disc
только при непустом identity.variantKey. При пустом альбомном контексте весь
этот блок пропускается, даже если ответ содержит сведения об альбомах. По снимку
нельзя подтвердить, какой ответ пришёл для конкретного файла: здесь установлен
потенциальный источник потери, а не доказана неполнота ответа Яндекса.

До версии 0.9.0 ссылка источника учитывалась в реестре, а набор записываемых и
проверяемых тегов не включал комментарий. Поэтому у загрузок прежних версий
могла отсутствовать ссылка, которую записывал старый скрипт.

## Последовательность внедрения

1. **Реализовано в 0.8.0:** развести источник сведений, уверенность разбора и полноту данных. Исправить
   фиксированный приоритет пути загрузчика и неоднозначное отображение 0.95/1.00.
   Для одинаковых тегов сканирование и загрузка должны давать одинаковый результат.
   Полнота показывается понятным отдельным индикатором; наличие значения само
   по себе не доказывает его правильность. Не требовать повторного массового
   Android-сканирования ради нового отображения.
2. **Реализовано в 0.9.0.** Сохранить альбомный контекст от коллекции до загрузки. При
   однозначно установленном релизе сохранять доступные альбом/год/жанр/номер.
   Не выбирать первый из нескольких альбомов наугад. Если релиз неоднозначен,
   хранить эту неопределённость. Добавить публичную ссылку Яндекса в записываемые
   теги и нативную проверку, сохранив неизменность аудиоданных.
3. Ввести общий расчёт полезной полноты: название/исполнитель, альбом,
   исполнитель альбома, год, жанр, применимые номера и обложка. Пустые значения,
   заглушки и некорректные числа не повышают оценку. Не штрафовать все записи
   одинаково за необязательные номера диска/релиза. Отличать фактические теги
   файла от догадок по имени и от сведений, дополненных в карточке приложения.
   При нехватке данных проверять кандидатов адресно, а не всю фонотеку.
4. После подтверждения одной записи выбирать предпочтительный пригодный файл:
   ручной выбор пользователя и правки → достоверные, более полные метаданные →
   аудиокачество. Битрейт сравнивается в сопоставимом кодеке/профиле и не служит
   единственным критерием. При автоматическом выборе более полный вариант может
   выигрывать у варианта с большим битрейтом. Это уточняет прежнее правило
   «скачивать при переходе на другое качество».
5. Для нового файла можно объединять преимущества: дополнять отсутствующие
   сведения из подтверждённого соответствующего старого файла, сохраняя звук
   без перекодирования. Перенос альбома/года/номеров/обложки требует установленного
   контекста релиза. Не перетирать конфликты и явно очищенные пользователем поля.
   Подготовку выполнять во временном файле с проверкой аудио до/после, новой
   проверкой полного хэша и атомарной публикацией по действующим контрактам.

## Правила совместимости и проверки

- Полнота не используется для доказательства совпадения треков. Совпадение
  подтверждается источниками/вариантом и, где необходимо, сравнением аудио.
  Разные исполнители, live/remaster/remix и разные релизы требуют разграничения.
- Выбор представителя не удаляет остальные файлы, их записи, оценки и связи
  с плейлистами. Данные существующего файла не переписываются фоном.
- Сохранение более полного старого файла не превращает его фактическое качество
  в заказанный более высокий профиль. Реестр и итог загрузки должны честно
  отражать результат выбора, а не подделывать подтверждение качества.
- При необходимости явного приоритета нового формата предусмотреть понятную
  настройку/явное действие; автоматический выбор следует новой метаданной политике.
- Проверки включают богатый/бедный набор при равном битрейте, более полный файл
  с меньшим битрейтом, placeholder-теги, ручные очистки, несколько альбомов,
  одинаковые названия разных записей, отказ подготовки и сохранение старой версии.
- Одни и те же синтетические примеры проверяются на Windows и Android. Для
  переподготовки подтверждаются одинаковые аудиопакеты/PCM и актуальные хэши.

Уточнение теста точных копий: счётчик сканирования не является результатом
дедупликации. При подключённых исходной и тестовой папках один побайтово
скопированный файл должен давать одну строку при скрытии точных копий и две
при их показе. Старый и новый файлы с разными тегами относятся к сравнению
вариантов композиции: полный файловый хэш у них различается.

## Шаг 1 в 0.8.0+2073

MetadataSource описывает происхождение карточки, metadataConfidence остаётся
эвристикой разбора, MetadataCompleteness отдельно считает заполненные основные
поля. Общая embeddedMetadataConfidence применяется сканером и строгими ридерами
публикаций Windows/Android. Полезные название/исполнитель дают 0.95 независимо
от числа дополнительных тегов; наличие только названия — 0.88, исполнителя
или альбома без названия — 0.82, отсутствие полезных identity-тегов — 0.2.
Это не калиброванная вероятность. Строгие ридеры всё ещё проверяют публикацию
и не выводят название/исполнителя из служебного имени файла.

Старые confidence 1.00 остаются в базе без массовой миграции. UI больше не
выводит их как оценку качества и не сортирует по ним. Для старых карточек
новый счётчик сразу вычисляется из уже доступных полей. Источник отображается
отдельно, подробная подсказка объясняет происхождение/недостающие поля.

В текущие N/7 входят полезные название, исполнитель, альбом, исполнитель
альбома, жанр, корректный год 1–9999 и непустая ссылка на встроенную/ручную
обложку. Пустые строки, известные заглушки и неподходящий год не засчитываются.
Номера трека/диска не входят в обязательный знаменатель: без контекста релиза
их отсутствие не считается недостатком. Несколько обложек не дают несколько
баллов. Битрейт, формат, длительность и confidence на N/7 не влияют.

Это **заполненность карточки**, включая ручные правки и догадки из имени.
Она не доказывает фактические теги файла, правильность, идентичность композиции
или существование картинки. Модель не делает IO, не проверяет пути и не
изменяет музыку. Сортировка «сначала неполные» — явное действие пользователя;
показатель вычисляется один раз на строку перед сравнением, не в каждом
вызове sort-компаратора. В обычной сортировке расчёт идёт только для видимых
строк. Геометрия/ленивая отрисовка списков сохранены.

Одновременно исправлен прежний пропуск Android: mergeAudioDocumentMetadata
и import controller теперь передают year/trackNumber/discNumber дальше.
Сырой snapshot v1 уже содержит эти поля, поэтому обычное обновление может
восстановить их из кеша без повторного MediaMetadataRetriever. Ручные очистки,
ID, плейлисты и пользовательская обложка сохраняют прежний приоритет.
Схема 15 и readerVersion 1 не меняются.

Шаги 2–5 описаны отдельно. Перед автоматическим предпочтением/пропуском
файлов потребуется подтверждённый источник/релиз и сведения о фактическом
файле: N/7 карточки нельзя подставить вместо этой проверки. Альбомный контекст,
публичная ссылка в тегах, сопоставление по качеству и перенос тегов в этом
выпуске не изменены.

## Шаг 2 в 0.9.0+2074

Метаданные берутся из релиза с ID, указанным в коллекции. Если в задании есть
только ID трека, подходит единственный релиз с корректным ID из ответа о треке.
При нескольких релизах без заданного ID дополняется только ссылка на трек.
Конфликт с явно заданным ID по-прежнему останавливает обработку. Ключ задания,
профиль качества и записи о предыдущих загрузках сохраняются. Если сервер
возвращает составной ID файла, его альбом должен совпасть с установленным
релизом. Доступные поля берутся отдельно с общим лимитом размера тегов.

Публичный комментарий строится из числовых ID на фиксированном домене.
Формат с альбомом используется при установленном релизе. Короткая ссылка
подходит при неизвестном релизе. Действует общий предел сканера в 32 цифры
на компонент ссылки. Подготовка файла проверяет точное совпадение комментария
вместе с другими тегами, а также совпадение аудиопакетов, декодированного звука
и обложки. Комментарий берётся с уровня файла для повторного импорта.
FFmpeg на Windows и Android использует формы записи, которые уже поддерживают
ридеры метаданных. Теги этой версии добавляются при новой загрузке.

## Сопоставление в 0.10.0+2075

При явном обновлении коллекций планировщик сначала проверяет зарегистрированные
загрузки. Для оставшихся заданий подбираются записи с внешним ID Яндекса в
подключённых папках или среди отдельно импортированных файлов. Для запроса
с релизом требуется совпадение ID альбома. Для запроса только с ID трека
допускается одна известная альбомная привязка среди доступных записей.
Несколько разных релизов оставляют выбор открытым. Подбор по названию,
исполнителю и битрейту без ссылки не используется.

Кандидаты проверяются по 64 ID за запрос, с просмотром до восьми копий на трек.
Плеер заново читает комментарии и проверяет, что внешний ID в файле совпадает
со связью библиотеки. Профиль определяется контейнером, аудиокодеком и нижним
порогом измеренного битрейта, принятым для того же профиля загрузки. Для FLAC
достаточно соответствующего контейнера и кодека. Среди подходящих копий сначала
сравнивается полнота встроенных сведений, затем битрейт. Счётчик карточки и
ручная обложка остаются сведениями интерфейса.

Windows использует штатный FFprobe и сравнивает размер и метки изменения до и
после проверки. Android открывает локальный файл по сохранённому SAF доступу
и проверяет его через нативный медиапомощник. Поддерживаются обычные файлы
провайдера внешнего хранилища с дескриптором всего файла. Проверка заголовков
используется вместо копирования, перекодирования или полного декодирования.
При ошибке чтения, конфликте комментариев или несовпадении формата работает
обычное планирование загрузки.

Транзакция применения сверяет актуальный план, сохранённую связь и запись
кандидата. Для подтверждённых копий новые задания не создаются. Прежние задания,
которые ещё не начинались, исключаются только из текущего запуска. После
удаления локальной копии следующий запуск сможет скачать её. Файлы не
записываются в реестр подтверждённых публикаций. Отчёт хранит лишь количество
пропущенных позиций.

## Версии в медиатеке с 0.11.0+2076

- «Моя музыка» группирует файлы с одним ID трека Яндекса. Известные разные
  альбомы остаются отдельными. Ссылка без альбома присоединяется только при
  одном известном альбоме или группируется с такими же ссылками при отсутствии
  сведений о релизе. Противоречивые ссылки и разброс известных длительностей
  более 2 секунд оставляют записи раздельными. Связь из ответа загрузчика
  используется, когда данные проверенной публикации совпадают с индексом файла.
- Сначала учитывается доступность и сохранённый выбор пользователя. Затем
  учитывается полнота карточки из тегов и ручных правок. При равной полноте
  используется проверенное качество загруженных файлов. Сопоставляются
  подтверждённый FLAC и, внутри одного кодека, проверенные пороги профилей.
  Когда сведений о качестве не хватает, выбор устойчив по исходному ID файла.
- Поиск находит группу по любой версии. Воспроизведение другой версии из окна
  подставляет её в ту же позицию списка без изменения основного варианта.
  Выбор хранится в базе приложения. При отключении папки или пропаже файла
  используется доступная версия. Оценки, история и состав плейлистов остаются
  привязаны к исходным файлам. Сортировка недавних прослушиваний учитывает
  историю файлов группы. При показе точных копий они доступны в окне версий.
- Группировка работает на существующем индексе, без нового чтения файлов и
  изменения схемы 15. Сравнение записей по звуку идёт следующим этапом.

## Сравнение звука в 0.12.0+2077

«Сравнить аудио» принимает два файла из подключённой библиотеки, включая
версии, скрытые группировкой. Для проверки используется SHA-256 всех
декодированных S32LE сэмплов с совпадающими частотой и числом каналов.
Медиапомощник читает MP3, M4A и FLAC с моно или стерео. Размер файла
ограничен 128 МиБ, длительность — 30 минут, общий срок задачи — 45 секунд.
Операцию можно остановить.

На Windows проверяются метки изменения файла. На Android используется
действующее разрешение SAF и отдельный дескриптор чтения обычного файла
провайдера внешнего хранилища. Теги и обложки
могут различаться, пока совпадает декодированный звук. При перекодировании
с потерями результат обычно различается. Проверка доступна по запросу и
показывает результат для выбранной пары. Автоматическое использование
результатов для группировки и приближённые отпечатки запланированы отдельно.

## Сохранение совпадений в 0.13.0+2078

- После точного совпадения доступна кнопка «Сгруппировать версии». Сравнение
  запоминает состояние источников до и после чтения. Для сохранения требуется
  неизменное состояние обоих файлов, доступ к ним и активные записи в индексе.
  На Windows сравниваются размер и файловые метки времени. На Android используется
  доступ и версия обычного документа через SAF.
- SQLite сохраняет две связи одной транзакцией в существующей схеме 15.
  Каждая связь относится к конкретному файлу, проверенному PCM и состоянию
  источника. При открытии библиотеки и обновлении соответствующей записи
  плеер перепроверяет состояние только ранее подтверждённых файлов.
  При недоступности или замене файла его связь перестаёт действовать.
- Совпавшие файлы без каталожной привязки образуют группу по точному PCM.
  Версия без ссылки может дополнить группу с одним подтверждённым релизом.
  Противоречащие каталожные привязки сохраняют отдельные строки. Для выбора
  основной версии и поиска действуют правила существующего окна вариантов.
- «Убрать связь по звуку» отменяет подтверждения для показанной группы.
  Исходные файлы, оценки и плейлисты используют прежние идентификаторы.
  При удалении индексной записи удаляется сохранённая связь этого файла.
  Настройки обновления из Яндекса используют исходные правила источника
  и профиля качества.

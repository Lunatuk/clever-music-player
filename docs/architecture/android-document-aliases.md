# Один SAF-документ через несколько папок (60)

## Причина

Один документ Android DocumentsProvider может иметь разные URI для разных
grants: /tree/parent/document/ID и /tree/child/document/ID. Сканер сохранял их
раздельно по полному URI, а Android preview передавал все строки в ListView и
очередь без общего фильтра desktop. Скачанный через child файл и его запись из
parent scan показывались дважды; у scan-записи также нет verified content hash.

## Правило идентичности

audioDocumentIdentity принимает только точную структуру DocumentsContract:
/document/ID либо /tree/TREE/document/ID. Ключ — (authority, documentId), grant
не входит. URI.pathSegments декодирует percent escapes ровно один раз, ID
остаётся непрозрачной строкой с учётом регистра. Разные providers/ID не равны.
Не выводятся filesystem paths, иерархия/вложенность, метаданные или совпадение
имён. Пустые ID, NUL, лишние сегменты, query/fragment и нераспознанные URI не
дают доказательства равенства. Произвольные MediaStore/provider URI не склеиваются
с SAF по внешнему сходству: без доказанной идентичности записи сохраняются.

## Отображение и очередь

withoutRepeatedAudioSources объединяет только такие aliases: доступная запись
предпочтительнее missing, затем меньший сохранённый ID, затем стабильный URI.
Результат не зависит от порядка включения корней или строк в SQL-ответе.
Фильтрация disabled folders выполняется репозиторием до этой операции: после
удаления parent выбирается действующий child URI и наоборот. Поиск также идёт
до collapse, так что найденная по своему полю запись остаётся воспроизводимой.

Общий withoutExactTrackCopies сначала устраняет aliases, затем по прежним
правилам проверенные физические byte copies. Режим showExactCopies оставляет
разные физические файлы, но один документ через два grants не дублирует. Android
preview применяет этот общий фильтр и передаёт тот же список в playLibraryTrack.
«Волна» уже использует общий фильтр, поэтому документ не получает двойной вес
из-за двух grants; оценки/формула/порядок подбора не изменены.

## Сохранность данных и границы

Это неразрушающее представление, как desktop exact copies: source rows и их ID
не объединяются, не перезаписываются и не удаляются. URI/grants, ownership,
manual metadata, user state/history, playlists и download Track/ref/asset/job/
receipts сохраняются. Разные registrations могут иметь свою старую метаинформацию
и состояние; слияние этих данных не выполняется. Новые мобильные экраны оценок/
редактирования должны учитывать это правило отдельно. Схема остаётся13.

Исправление действует на существующей БД сразу после запуска60: rescan/hash/
redownload/migration не нужны. При обоих disabled roots файл скрыт, если нет отдельного явного
импорта этого документа через standalone grant. При оставшемся
корне, через который документ ещё никогда не индексировался, alias не изобретается:
для этого корня по-прежнему нужен обычный импорт. Доступ проверяется player/SAF;
отключённые и пропавшие записи не объявляются доступными из-за одной идентичности.

Код не удаляет реальную музыку и не принимает решение о равенстве разных файлов
по названию/размеру/артисту. Полный SHA-256 разных физических файлов остаётся
самостоятельным доказательством по прежнему контракту, когда такой hash известен.

## Проверки

Unit: разные tree grants и direct document, escape case/однократное decoding,
opaque IDs/provider isolation, malformed/unknown addresses, missing preference,
детерминированный представитель, search/showCopies и сохранение byte-copy правил.
SQLite: обе последовательности удаления roots, restart, legacy adoption без
scan, reactive streams, все исходные ID/feedback/history/playlist links сохранены.
Widget: одна строка/правильный URI и полный context очереди, смена действующего
alias, 6000 строк/прыжки списка при масштабе1/2. Recommendation: один кандидат.
MP3/M4A/FLAC loopback pipeline: после download добавлен scan alias, виден один
трек, verified asset остаётся у исходной записи и повтор не делает HTTP download.
Host FFmpeg и file-backed provider не считаются новым Android runtime test.

Физическая проверка60 требуется на существующих вложенных папках Redmi. После
неё ближайший блок — основные мобильные экраны и варианты общего редизайна,
а расписание и улучшение рекомендаций не блокируют этот перенос.

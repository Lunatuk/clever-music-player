# Единый ключ полного файла — 0.4.1

Версия 0.4.1, сборка 2067, схема SQLite 14.

FileContentIdentity задаёт один формат Track.contentHash:
`file-sha256-v1:<размер в байтах>:<SHA-256 в нижнем регистре>`.
В нём учитываются все байты, включая теги и обложки. Названия, подписи
метаданных и ID Яндекса не являются файловым хэшем. Изменение тегов или
другое качество создаёт другой файловый ключ; группировка композиции —
самостоятельный будущий механизм.

Сканер использует этот формат с прежних версий. Теперь его используют также
Windows/Android-подготовка скачанного Track и DownloadedTrackImport. Старый
подготовленный Track с голым SHA-256 допускается только при точном совпадении
с предоставленным подтверждением размера/хэша и нормализуется до записи.

DownloadedAssetVerification.contentHash, SourceFingerprintResult.digest,
публикационные журналы и нативные каналы сохраняют прежний голый SHA-256.
Методы verification.fileContentKey и matchesContentHash связывают эти формы
только в контексте явного подтверждения файла. Реестр, выбор кандидатов,
повтор атомарного импорта и разрешение очистки журналов понимают обе формы.
Подмена размера или байтов не становится совместимой из-за нового префикса.

## Перенос базы

При переходе на схему 14 короткая транзакция обновляет только Track.contentHash
у доступных старых загрузок: нужен verified-ресурс с тем же точным источником,
известным положительным целым размером, SHA-256 и внешней ссылкой этого трека.
Неподтверждённые 64-символьные значения, отсутствующие/недоступные/невалидные
ресурсы и несоответствия остаются без изменений. Файлы не читаются и не меняются.

Размер/хэш подтверждения загрузки, ревизии, очередь, попытки, внешние ID,
плейлисты, история, оценки, обложки и ручные поля сохраняются. Смена формата
и маркер версии фиксируются вместе; отказ откатывает оба изменения. Снимок DDL
схемы 13 экспортирован из проверенной 0.4.0 и сохранён отдельно для тестов.
Старая версия приложения со схемой 13 не предназначена для открывания базы 14.

Реестр при новой физической проверке также нормализует совпадающий известный
legacy-хэш. Неизвестный Track-хэш не изобретается самим реестром. Общий фильтр
копий принимает только версионированные ключи; если в Track известен размер,
он должен совпадать с размером ключа. Представление не удаляет записи или файлы.

Обычный Android SAF-импорт по-прежнему не хэширует все файлы. Дополнительного
полного прохода по музыке и повторного сканирования ради миграции не требуется.
[Оптимизация Android-обработки](android-import-performance.md) идёт следующим
этапом. Перед автоматическим выбором загрузок следует
[блок метаданных и предпочтения файлов](metadata-file-preference.md): полезная
полнота приоритетнее битрейта при установленном соответствии записи.

## Проверки

Проверяются границы формата, неизвестные значения, подмена размера, реальные
байты файлов, scanner/download-сопоставление, проверка доступности после
сканирования, повтор импорта и отсутствие повторной публикации. Нативные
MP3/M4A/FLAC-сценарии проверяют отдельно canonical Track и raw digest реестра.

Миграции со схем 1–13 используют замороженные DDL. Для схемы 13 проверяются
Windows и SAF, сохранение остальных строк/полей, неизвестные/повреждённые
подтверждения, очередь с активной попыткой, атомарный отказ, повтор и перезапуск.
Тесты используют изолированные файлы/базы; личная фонотека не нужна.

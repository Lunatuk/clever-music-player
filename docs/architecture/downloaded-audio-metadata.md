# Подготовка тегов и обложки скачанного аудио

Пакет 33, 16 октября 2026, схема 13. Это внутренний desktop-модуль, ещё
не подключённый к AppDependencies, сети или кнопке обновления. Обычный запуск
и воспроизведение не запускают FFmpeg; бинарники пока не поставляются.
Android content URI требует отдельного адаптера и возвращает unsupportedSource.

## Владение и последовательность

DownloadedAudioMetadataPreparer принимает FileAudioSource, уже эксклюзивно
принадлежащий операции загрузки, и DownloadedAudioExpectation. Его размер
относится к исходнику, а теги — к ожидаемому результату. Это не редактор
существующей фонотеки: исходник читается, выход всегда находится в новой
private directory с собственным случайным именем.

1. Проверяются тип/размер и полный SHA-256 исходника; backend определяет
   фактический контейнер/кодек. Допускаются MP3/MP3, M4A/AAC, FLAC/FLAC.
2. Сохраняются SHA-256 сжатых аудиопакетов и всего декодированного PCM S32LE.
   Первый сравнивает encoded payload; второй ловит изменение decoder context,
   числа сэмплов и обрезки encoder delay/padding при remux.
3. Создаётся собственный каталог; только в нём резервируется audio.part.
   Новая PNG/JPEG-обложка копируется из immutable snapshot в cover.part.
   Если замена не передана, прежняя attached_pic сохраняется. Отсутствие
   обязательной обложки отклоняется, вариант без неё разрешается явно.
4. FfmpegAudioMetadataBackend выполняет stream copy в этот новый файл:
   заданные восемь видов тегов, одна обложка, явный muxer, без кодирования аудио.
   MP3 использует ID3v2.4; M4A — ipod/faststart; FLAC — родной muxer.
   Обложка помечается front cover. Унаследованные provider tags/chapters
   заменяются ожидаемым набором, а не переносятся неявно. Ручные DB-правки
   пользователя к этому модулю не относятся.
5. DownloadedAudioValidator проверяет результат с его фактическим новым
   размером: кодирование/политику, ожидаемые теги/длительность, полное
   декодирование аудио/картинки и стабильный полный SHA-256.
6. Сверяются sample rate/channels/bit depth, encoded audio и PCM до/после,
   точные encoded bytes картинки (с переданным snapshot либо прежней обложкой).
   Неожиданная обложка без исходника/замены также отклоняется.
7. Повторно проверяются полный SHA-256/размер/даты исходника и итоговый
   SHA-256/размер выхода после последних backend-процессов.
8. Только затем возвращается PreparedDownloadedAudio с inspection и
   DownloadedAssetVerification. Владение временными файлами передано вызывающему.

Готовый файл передаётся publisher через writeAudio(openRead(), expectedSize),
затем publish с тем же proof. Publisher повторяет полный hash перед физическим
эффектом и проверяет актуальное владение заданием. Эта дополнительная копия
пока сознательна; оптимизация adoption должна сохранить file ownership/fence.
Ни preparer, ни такой поток сами не создают Track и не завершают job в БД.

Обоснование FFmpeg:
[stream copy](https://ffmpeg.org/ffmpeg.html#Streamcopy),
[hash muxer с явным copy/PCM](https://ffmpeg.org/ffmpeg-formats.html#hash),
[метаданные и явное сопоставление потоков](https://ffmpeg.org/ffmpeg.html).
Это проверка сохранности аудио, не идентификация песни по звучанию или
доказательство того, что провайдер вернул нужный remote ID.

## Ограничения и завершение

Одна операция/один процесс одновременно; shared hash worker переиспользуется.
Исходник/выход до 8 ГиБ, длительность до 12 ч, новая картинка до 8 МиБ с
JPEG/PNG signature, итоговый размер картинки до 4096×4096 по validator.
Картинка копируется после проверки размера, snapshot недоступен для изменения.
Каждый тег до 4096 UTF-16 units, сумма значений до 8192 для argv Windows.
Значения передаются отдельными аргументами, без shell; формат не выводится
из расширения .part. Протоколы file/pipe, ограниченные demuxers, max_alloc
64 МиБ/потоки 1, ограниченный stdout/stderr из прежнего MediaProcessRunner.
Это не общий OS sandbox или гарантия совокупного RSS.

Общий timeout по умолчанию 10 мин, максимум 30 мин. Отмена/close прекращают
приём и дренируют принятый вызов, включая забытый await, затем закрывают
backend/hash session. Они не бросают работающий child или writer Future.
Системный вызов/start/внешний backend может потребовать времени для завершения;
жёсткого wall-clock лимита зависшего OS IO нет. Typed failures не содержат
stderr, путей, тегов, токенов или произвольного текста исключений.

При отказе удаляются только audio.part/cover.part и пустой собственный каталог;
рекурсивного удаления нет. Неизвестные файлы не стираются, ошибка удаления
остаётся отказом. Доставленный результат живёт отдельно от preparer: владелец
вызывает result.close после завершения всех чтений/публикации. Close идемпотентен.
Авария процесса может оставить private temp: журнал/retention будущего
координатора должен владеть такими ресурсами, startup cleanup пока отсутствует.
Исходник обязан оставаться эксклюзивным для операции; хэши замечают обычные
изменения, но это не защита от враждебных подмен путей между системными вызовами.

## Совместимость общего reader

Выявлено смешение ролей: MP3 предпочитал TPE2 перед TPE1, Vorbis складывал
ALBUMARTIST в список ARTIST, M4A не читал aART. Теперь generic AudioMetadata
имеет albumArtist; MP3 предпочитает TPE1, M4A читает ©ART/aART раздельно,
FLAC/OGG разделяют ARTIST и три распространённых spelling album artist.
Если main artist отсутствует, полезный album artist сохраняется как fallback.
APE передаёт существующее одноимённое поле. Общий background reader передаёт
albumArtist в уже существующую модель импорта; автоматической перезаписи
прежних записей/ручных правок нет, миграция не требуется.

FLAC/MP4 serializers сохранены совместимыми с новым полем. В FLAC найдены
два прежних дефекта: потеря last-block flag при замене последней картинки/
комментария и значение 255 вместо бита 128. Теперь копируемые блоки nonfinal,
последним идёт явный пустой padding; STREAMINFO-only input получает комментарии.
Reader закрывается в finally до записи. Эти низкоуровневые in-place writers
по-прежнему не используются preparer и не объявляются общим безопасным
редактором пользовательских файлов.

## Проверки и следующий этап

58 новых Flutter-проверок: 25 ownership/lifecycle/failure/publication,
19 helper protocol и 14 независимых parser/serializer fixtures. Последние
содержат только container/tag структуры, не playable audio. Полный набор —
1258 passed с concurrency=4; исходный default-concurrency прогон дал timeout
старого теста 70 journal fsync и его последующую каскадную ошибку. Отдельный
набор диагностики 12 passed; test deadlines не увеличивались.

tool/check_downloaded_audio_metadata.dart запускается офлайн с двумя явными
путями к ffprobe/ffmpeg и создаёт свою systemTemp-фонотеку. FFmpeg 7.1: 31
проверка реальных MP3/M4A/FLAC, Unicode/кавычек/восьми тегов, JPEG/PNG,
сохранения/замены/отсутствия картинки, decoded/encoded equality, настоящего
reader, FLAC serializer, OGG role compatibility, повреждённых данных,
неподходящего формата, отмены, отсутствующего helper и очистки ресурсов.

Реальная проверка обнаружила, что frames:v=1 в remux может преждевременно
остановить аудио. Лимит убран именно из remux: конечный validator/PCM сравнение
обязательны. Ограничение одного кадра остаётся в отдельном digest/decode cover.
Windows проверен; macOS и физический Android/SAF writer здесь не проверялись.
Далее — квалифицированная поставка helper с исходниками/лицензиями, coordinator,
атомарный import и retention, затем сеть/вход/коллекции/кнопка. Для нового
бинарника повторяются native fixtures; системный C:\ffmpeg не становится
зависимостью установленного плеера.

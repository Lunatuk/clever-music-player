# Проверка нового аудиофайла перед публикацией

Пакет 30, схема 13. `DownloadedAudioValidator` проверяет завершённый staging
файл после записи тегов/обложки. Он не изменяет файл, не импортирует Track,
не пишет в SQLite и не завершает задание. Вызывающий будущий координатор владеет
staging-ресурсом, backend, временем жизни сервиса и правом публикации.

Пакет 29 подтверждает прежние свойства только при совпадении всех байтов.
Пакет 30 проверяет свойства нового файла и создаёт `DownloadedAssetVerification`
только после всех успешных этапов:

1. Ожидаемый размер и допустимый файл, полный SHA-256.
2. Реальные контейнер/кодек, длительность, размер, sample rate/channels и теги.
3. Соответствие явной политике выбранного кодирования и ожиданиям провайдера.
4. Декодирование всего аудиопотока без вывода звука, положительная длительность.
5. Если есть встроенная обложка, декодирование её кадра; если она обязательна,
   отсутствие обложки не пропускается.
6. Второй полный SHA-256 и сверка размера/дат с первым чтением.

Это не измерение музыкальной идентичности/похожести. Ожидаемые provider/ID,
длительность и политика формата приходят от доверенного адаптера загрузки.
По одинаковой длительности и тегам нельзя доказать, что сервер прислал именно
нужную песню. Качество не выводится из расширения или имени категории.

`DownloadedAudioExpectation` задаёт opaque quality, допустимую пару mp3/mp3,
m4a/aac или flac/flac, ожидаемые байты, длительность, нужные теги, минимальные
bit rate/sample rate/bit depth и требование обложки. Для lossy обязателен явный
минимальный bit rate; неизвестное числовое свойство не удовлетворяет минимуму.
Lossless может требовать глубину 16/24 bit. Числовые пороги должен обосновать
адаптер конкретного выбранного варианта; текущий код не объявляет готовыми
правила категорий Яндекса. VBR нельзя без исследования сравнивать с номинальным
CBR как одинаковые профили. Нет скрытого понижения качества.

Максимум 8 ГиБ и 12 часов, 1–8 каналов, sample rate 8–192 кГц. Допуск длительности
по умолчанию 500 мс, явно настраивается в диапазоне 0–10 с. И заявленная,
и реально декодированная длительность сверяются с ожиданием; между собой также.
Обрезанный файл может иметь согласованный размер полученного HTTP-тела,
поэтому один размер не заменяет декодирование/длительность. Потери в пределах
заданного допуска и ошибки, которые декодер не обнаруживает, этим не исключены.

Теги title/artist/album/album_artist/genre/track/disc/date копируются в immutable
карты. Ключи ffprobe приводятся к lowercase, albumartist — к album_artist;
противоречащие значения из разных мест не выбираются молча. Значения ожидаемых
тегов сравниваются точно, без filename fallback, каждый до 4096 символов.
Полученные теги используются как результат проверки, а не как команды.

`AudioValidationBackend` изолирует inspect/decodeAudio/decodeCover/close.
Первый реальный адаптер — `FfmpegAudioValidationBackend` для desktop.
Он получает абсолютные пути к ffprobe/ffmpeg явно, не использует PATH, Python,
локальный D:\YaDown, сетевую установку или декодеры активного PlayerService.
Исполняемые файлы должны поставляться/проверяться будущим владельцем помощника.
В этом пакете они не вложены в ZIP/APK и не подключены в AppDependencies:
обычный запуск и проигрывание не запускают процессы проверки.
Нет поддержки content URI: возвращается unsupportedSource; Android потребуется
нативный backend чтения/декодирования с тем же контрактом доказательства.

ffprobe сообщает только нужные поля формата/потоков и теги. Поддерживается один
аудиопоток и максимум одна attached_pic JPEG/PNG до 4096×4096. Обычный видеопоток,
лишние потоки, неизвестные форматы, неоднозначные индексы/теги и неверные типы
отклоняются. Произвольный video stream не считается обложкой.
[Документация ffprobe](https://ffmpeg.org/ffprobe-all.html).

FFmpeg читает выбранный аудиопоток до конца в null muxer, с xerror, нулевой
допустимой долей ошибок и err_detect crccheck+bitstream+buffer+explode. Проверяется
финальный progress=end и положительный out_time_us, а не просто exit code 0.
Для аудио asetpts=N/SR/TB строит непрерывное время по числу декодированных
сэмплов: скачок входных PTS не подменяет отсутствующие сэмплы. Регрессия с
двумя секундами AAC и трёхсекундным разрывом PTS воспроизвела ложный успех
без фильтра, после исправления отклоняется.
[FFmpeg: sample timestamps](https://ffmpeg.org/ffmpeg-filters.html#asetpts).
Обложка декодируется отдельно, ожидается один кадр. Это проверка декодируемости,
не перекодирование пользовательского файла.
[FFmpeg: progress/xerror](https://ffmpeg.org/ffmpeg.html).

Ограничены demuxers mp3/mov/flac, protocols file/pipe, число потоков 2,
probesize 2 МиБ, analyzeduration 10 секунд, отдельное выделение памяти 64 МиБ,
потоки decoder/filter 1. Это ограничения конкретного помощника, не обещание
общего лимита памяти или OS sandbox. Для неподдерживаемого/неквалифицированного
бинарника нужна проверка совместимости при будущей упаковке.
[FFmpeg formats](https://ffmpeg.org/ffmpeg-formats.html),
[FFmpeg protocols](https://ffmpeg.org/ffmpeg-protocols.html).

`BoundedMediaProcessRunner` запускает без shell, с отдельными аргументами;
stdin закрыт, stdout и stderr дренируются параллельно. Лимиты по умолчанию
256/64 КиБ, переполнение прекращает процесс и не накапливает дальнейший вывод.
Произвольный stderr не сохраняется/не экспортируется; фиксированные типы
отличают недоступный executable, ошибку IO и переполнение. Ненулевой exit или
error-level stderr не принимается как успех. После завершения процесса сигнал
повторно не отправляется; при отмене посылается kill, ожидаются exit и оба pipe.
Отмена при незавершённом Process.start применяется сразу после получения child.

Один validate, один child; параллельные команды отклоняются. Общий timeout
10 минут, допустим до 30; close закрывает приём, запрашивает отмену и дренирует
все принятые операции, затем пытается закрыть hash session и backend вместе.
Не бросаются работающие Future. Таймаут процесса/start/IO кооперативен относительно
ОС; жёсткого обещания длительности зависшего системного вызова нет.
Ошибки/отмена не содержат verification. Файл не удаляется при отказе.

Проверка не держит блокировку назначения; внешний процесс может изменить файл
после её окончания. Для следующего шага нужны закрытый staging writer,
блокировка/fencing, журнал публикации и повторная сверка итогового источника.
Проверенное временное имя ещё не равно опубликованному доступному ресурсу.

Автотесты используют временные файлы, фальшивые backend/runner и настоящие
дочерние Dart-процессы. Windows-прогон `tool/check_downloaded_audio.dart` создаёт
свои MP3/M4A/FLAC, PNG/JPEG, проверки расширения/политики/тегов/отсутствия обложки,
повреждённой картинки, обрезания и отсутствия executable. Два явных аргумента:
абсолютные пути ffprobe и ffmpeg. Пользовательская музыка/БД не открываются.
Локально проверен FFmpeg 7.1; macOS и Android backend здесь не испытывались.
Поставка помощника (включая лицензии/исходники/совместимость), запись тегов/обложек,
публикация, сетевой адаптер и UI ещё впереди.


## Продолжение: staging и публикация (пакет 31)

Добавлены desktop workspace, OS-lock/SQLite fence, журнал и публикация без
замены файлов. Валидатор вызывается после закрытия metadata writers, до
публикации. [Контракт](desktop-file-publication.md). Полный helper bundle,
запись тегов/обложек и атомарный импорт остаются следующими шагами.

## Продолжение: запись метаданных (пакет 33)

Внутренний preparer пишет новые теги/обложку в отдельный private output,
вызывает этот validator с фактическим размером результата и затем сверяет
пакеты аудио, декодированные PCM и байты картинки. Исходник не подменяется;
в конце повторно проверяются полный source/output SHA-256.
[Контракт подготовки](downloaded-audio-metadata.md). Helper bundle и
координатор/UI по-прежнему следующие шаги.

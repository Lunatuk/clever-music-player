# Первичный импорт: пакет 11

Оптимизация разделена на проверяемые шаги: замеры/теги/обложки/Windows SHA-256, затем пакетные записи SQLite и обновления списков, затем постоянные исполнители/другие платформенные адаптеры и отдельные измерения кадров Flutter. Первое изменение уже сохраняет общие правила библиотеки и прежнюю семантику остановки.

## Измерения

`ScanMetricsRecorder` использует Stopwatch и суммирует непересекающиеся участки: полный хэш, метаданные, кэш обложек, обращения к БД. Учитываются awaits, запуск рабочего isolate и неуспешные попытки. В пакете 12 отдельно измеряются обход/stat/повторная проверка файла (`fileSystemUs`). Остальные задержки остаются в общем elapsed; суммы этапов не обязаны заполнять всё время. `metadataReads` различает первичный и неизменившийся повторный проход. Объём/число хэшей относится к завершённым проверкам, частичное чтение прерванного файла не выдаётся за подтверждённые байты.

Снимки прогресса содержат метрики; общий обход складывает метрики предыдущих папок. UI показывает среднюю скорость обработанных файлов и подтверждённого объёма относительно общего времени. Это не мгновенная скорость диска и не процент готовности всей коллекции. Диагностика записывает только фиксированные числовые поля `hashUs`, `metadataUs`, `artworkUs`, `databaseUs`, `hashedBytes`, `hashedFiles`, `nativeHashFiles`, `metadataReads`, `fileSystemUs`, `importBatches`, `importRows`; пути и теги не добавляются.

## Windows SHA-256

`Sha256Digest` отделяет операцию хэша от файлового обхода. Windows использует `bcrypt.dll`/CNG через FFI; другие платформы и отказ инициализации провайдера используют прежний пакет crypto. Ошибка уже начатого native-хэша прерывает проверку, частичный результат не публикуется. Инициализация/завершение освобождают буферы, hash handle и algorithm provider. При остановке файл закрывается через прежний finally, затем освобождается digester; принудительного Isolate.kill нет.

В пакете 11 IO-блоки были 64 KiB; пакет 13 использует ReadInto с буфером до 256 KiB (малые файлы — меньше), при внутреннем CNG-буфере 64 KiB. Контроль размера/mtime/change time до/после чтения и после тегов не ослаблен. Backend не входит в ключ `file-sha256-v1:<размер>:<digest>`, поэтому существующие идентичности файлов/обложек совместимы. Принудительный `preferNative: false` используется для сравнительных проверок и benchmark. API и порядок освобождения сверены с [документацией CNG](https://learn.microsoft.com/en-us/windows/win32/seccng/creating-a-hash-with-cng).

## Теги и обложки

Штатный парсер запускается через Isolate.run; вызывающий код ожидает его завершения, включая при запросе остановки. Внедрённые callback-адаптеры для тестов/специальных источников сохраняют прежний контракт. Данные тегов/картинки возвращаются без изменения. Парсинг больших/повреждённых тегов в этом пакете не получил жёсткого таймаута/принудительного обрыва.

Проверки реальных ошибок выявили незакрытый file reader в `audio_metadata_reader` 1.6.0 при неподдержанном формате и ошибке FLAC picture. Локальная копия ранее установленного пакета, с лицензией и SHA-256 исходного снимка, добавляет владельца `OwnedFileReader` в оба публичных entry point и закрытие в finally. Уже закрывший reader контейнер не приводит к повторному закрытию; сопоставление текста исключений не используется. Общий pub cache не изменяется. См. `third_party/audio_metadata_reader/CLEVER_PLAYER_PATCH.md`.

Кэш обложек вычисляет совместимый SHA-256 (на Windows также CNG), затем асинхронно проверяет ожидаемое имя и конечный набор прежних расширений jpg/jpeg/png/webp/gif/tif/tiff/bmp/bin. Полного перечисления каталога и синхронной проверки каталога на каждой обложке больше нет. Каталог создаётся только при новой записи; удалённая снаружи обложка создаётся заново. Embedded/custom каталоги остаются раздельными. Файлы исходной музыки не изменяются. Это не реализация garbage collection/квоты картинок или новой общей модели ресурсов.

## Условия оценки

`tool/benchmark_file_hash.dart` сравнивает два backend на одном синтетическом файле 16 МиБ, проверяет одинаковый ключ и считает медиану семи операций после прогрева. Исполняемый файл компилируется AOT; учитываются IO, запуск/завершение worker. Данные только что записаны в системный temp на SSD и, вероятно, находятся в кэше ОС. Результат не заменяет замер настоящего импорта.

`tool/benchmark_artwork_cache_test.dart` — отдельный Flutter-тест, не обычный regression suite: временный кэш 100/1000/4000 файлов, 50 повторных lookup, медиана/p95. Это debug/JIT-измерение одной операции. Regression-тест запрещает перечисление каталога независимо от времени выполнения. Следующее решение о SQLite/UI принимается по числовому отчёту настоящей новой коллекции, с учётом форматов, объёма, активных подписок и типа накопителя. macOS/Android требуют своих измерений на той же версии приложения.

На той же библиотеке неизменившийся повтор пропускает теги/обложки, поэтому его нельзя выдавать за первичный импорт.

`TrackImportRepository.upsertScannedTracks` принимает не более 64 уже подготовленных записей с уникальными путями. Drift в одной короткой транзакции получает актуальные строки по путям, пишет пакет и возвращает ID в порядке входа. Совпадение музыкальных тегов/хэша не разрешает перезапись другого пути. Сохраняются ID, владелец источника, addedAt, все актуальные ручные поля (включая null), установленная или очищенная пользовательская обложка. SQL companion передаёт null явно, без неоднозначного copyWith. Пользовательская статистика, события и плейлисты не заменяются; INSERT OR REPLACE не используется. Существующий общий upsert для иных операций сохраняет прежний контракт.

Сканер буферизует только небольшие модели/ссылки, без аудиоданных/картинок: максимум 64, периодическая запись после 750 мс между файлами. Это не параллельный таймер и не гарантия сохранения ровно через 750 мс при зависшем следующем IO. При завершении/остановке/ошибке обхода готовый остаток сохраняется. Текущий незавершённый файл отбрасывается; уже начатая запись дожидается результата. Штатное закрытие контроллера дренирует работу до закрытия БД. Принудительное завершение процесса может потерять незаписанный буфер. Транзакция не охватывает хэширование/чтение тегов/обложек/ожидание каталога. Перед записью повторно проверяются размер/mtime/change time подготовленных файлов: изменение/удаление в буфере не публикует устаревший хэш.

Ошибка транзакции откатывает весь пакет. Затем короткие одиночные попытки отделяют проблемный файл от остальных; счётчики добавлений/обновлений и `importRows`/`importBatches` увеличиваются только после успешной записи. У ранее известного ошибочного файла сбрасывается неподтверждённая идентичность, он не становится отсутствующим. Совместимые адаптеры без пакетного интерфейса продолжают одиночную запись. Незавершённый обход не отмечает непросмотренные файлы отсутствующими и не обновляет дату полного обхода.

Подписка «проиндексировано» использует COUNT всех файловых записей (включая missing/disabled) вместо второго списка тегов/обложек. ID для подписки оценок упорядочены независимо от порядка строк: смена сортировки метаданных не пересоздаёт запрос. Полный активный список пока сохраняется; сокращение его перезагрузок достигается общей транзакцией на пакет, без глобальной паузы наблюдений. Лайки и пользовательские изменения остаются интерактивными. Новые числовые метрики не содержат путей/тегов/секретов и не меняют схему БД.

`tool/benchmark_import_database_test.dart` сравнивает прежний одиночный upsert + два полных списка и пакеты 16/64 + список/COUNT. Каждая свежая файловая БД работает через NativeDatabase.createInBackground, имеет 1000 исходных строк и получает 1000 подготовленных; активны обработчик сортировки/дедупликации списка и запросы оценок. Между подготовленными строками передаётся управление event loop; после каждой транзакции инструмент ожидает актуальный список, счётчик и запрос оценок. Это намеренно исключает случайное объединение почти всех уведомлений плотным циклом и задаёт воспроизводимый сценарий одного видимого обновления на commit. Это Flutter debug/JIT и один замер на вариант; нет чтения музыки, тегов/обложек, звука и реальных Flutter-кадров. Он проверяет выигрыш записи/запросов, не обещает такую же скорость всей реальной коллекции. Базу пользователя инструмент не открывает. Следующая оценка полного импорта — по новому реальному отчёту.

Финальный последовательный запуск на Windows, без одновременных тестов/анализа: прежняя запись 1000 строк — 85 125,801 мс и 1000 обновлений каждого подписчика; пакет 16 — 3106,335 мс и 63 обновления; пакет 64 — 3442,413 мс и 16 обновлений. Это один JIT-замер, поэтому разница 16/64 не устанавливает оптимальный размер пакета. Предварительные плотные циклы (37–39 с для одиночной записи) объединяли уведомления почти до двух; они не используются как итог интерактивного сценария. Лог финального запуска: `.dart_tool/import12-database-benchmark.log`.

## Пакет 13: жизненный цикл hash-worker и профиль

`SessionFileContentHasher` открывает `FileContentHashSession`; штатный SHA-256 возвращает одну лениво запускаемую `Sha256HashSession` на сканирование папки. Сервис вызывает close в finally, затем формирует итог/диагностику с полной длительностью, включая очистку. Новая папка следующего обхода получает новую сессию. При нескольких независимых сервисных вызовах сессии не разделяют отмену/состояние. Контроллер приложения сохраняет прежнее ограничение конкурентных команд. `reuseHashWorker: false` оставляет одиночный путь для сравнений; адаптеры без интерфейса работают по прежнему контракту.

Сессия принимает один активный запрос; конкурентный запрос немедленно отклоняется, очереди файлов нет. Рабочий порт последовательно принимает пары path/replyPort, а каждый файл получает отдельный активно слушаемый cancellation port. Это позволяет отменять IO, пока основной stream worker ждёт текущий файл; старые сообщения не попадают в следующий запрос. Ответ отправляется после закрытия RandomAccessFile/канала команд. Обычная отмена сохраняет worker для следующего вызова, close отменяет активную работу, дожидается её и запрашивает штатный выход. Принудительного Isolate.kill нет. Fatal error/exit контролируются отдельным lifetime-портом, незавершённый запрос получает ошибку; аварийное завершение VM/процесса не обещает штатного cleanup. Конструкторный entry-point override используется только контрактными тестами с worker без открытых файлов.

Вместо нового массива на каждом read используется ReadInto с одним буфером на файл: минимум 1 байт, максимум 256 КиБ штатно, не больше исходного размера для малых файлов. CNG продолжает принимать данные внутренними блоками 64 КиБ. После EOF проверяются полный размер/mtime/change time; рост обнаруживается и до EOF. Публичный ключ SHA-256/побайтовое доказательство совпадения/ID/правила копий не меняются. Исходная музыка не изменяется. Общие векторы и оба backend проверены также с повторным использованием буфера; весь файл в память не загружается. Параллельное хэширование нескольких файлов не введено.

Подробные поля хэша поступают с подтверждённым fingerprint: `hashReadUs` — stat/open/read/close/stat с await, `hashComputeUs` — создание/add/finish/dispose digester, `hashWorkerUs` — всё внутри hash-функции, `hashOverheadUs` — остаток parent round trip, `hashStartupUs` — ожидание готовности нового worker, `hashWorkerStarts` — учтённые старты. Startup после ошибочного/отменённого первого файла переносится в следующий успешный ответ той же сессии. Без успешного ответа подробности не публикуются, но полное время попытки остаётся в hashUs. Поэтому профили рассматриваются в сумме обхода, не как независимые слагаемые каждой строки. IO/compute — wall time с возможным планированием, не чистое время накопителя/CPU; workerUs включает read/compute, startup входит в накладные расходы. У старого одиночного режима timestamp получения ready может пересечься с уже начатой работой worker, его нельзя дополнительно прибавлять к total.

`databaseLookupUs` охватывает снимок известных треков и поиск пути; `databaseImportUs` — пакетное сохранение включая актуальный lookup/commit/возврат ID; `databaseMaintenanceUs` — подготовку источника/seen/missing/hash/даты. Эти три участка вложены в databaseUs, включают await/обмен/маппинг, а также неуспешные попытки. Они нужны для выбора следующей оптимизации по настоящему отчёту, не означают чистую длительность SQL на worker. Схема БД/зависимости не изменены.

`tool/benchmark_hash_worker.dart` — AOT, три повтора и медиана, временные синтетические файлы (64 × 64 КиБ, 32 × 4 МиБ, 8 × 16 МиБ), тёплый кэш ОС вероятен. Сравниваются одиночный путь 64 КиБ и сессия с лимитом 64/256; совпадение ключей обязательно. Отдельный baseline executable скомпилирован до изменения production-исходников и сохраняет код пакета 12, поэтому доступно сравнение и с прежним read(). Финальный последовательный замер, мс:

| Набор | Пакет 12, старый executable | Новый одиночный 64 | Сессия 64 | Сессия до 256 |
| --- | ---: | ---: | ---: | ---: |
| 64 × 64 КиБ | 62.836 | 46.945 | 37.692 | 38.284 |
| 32 × 4096 КиБ | 279.086 | 263.245 | 251.273 | 165.727 |

# Ссылки на аудиоисточники

Пакет 16, 13 октября 2026 года. Общая граница воспроизведения обычного файла и Android content URI. Схема SQLite остаётся 9; миграции и перезаписи существующих адресов нет.

## Модель и хранение

`AudioSourceReference` — неизменяемое значение двух типов:

| Тип | Адрес | Доступ к аудио |
| --- | --- | --- |
| `FileAudioSource` | Обычный путь Windows/macOS/Android, включая UNC и относительный путь | Прежняя проверка файла, нормализация для воспроизведения, Windows-кэш при необходимости |
| `ContentUriAudioSource` | `content://authority/path` | URI передаётся Android-аудиодвижку, без File.exists/stat и Windows-кэша |

`Track.source` восстанавливает тип по адресу. `Track.fromSource` создаёт запись из проверенного значения и сохраняет все поля метаданных; `copyWith(source: ...)` явно меняет адрес. Одновременно передать `source` и `filePath` нельзя. Старый const-конструктор `Track(filePath: ...)`, сравнение записей и импорты сохраняют совместимость.

В этой промежуточной схеме адрес по-прежнему хранится в колонке `file_path`: обычный путь или исходная строка content URI. Все прежние пути, ID, хэши, метаданные, внешние ключи и настройки остаются прежними. Репозиторий использует точное значение адреса; регистр, кодирование и разделители URI в БД не нормализуются. Отдельная модель источника библиотеки/файлового ресурса и разрешений остаётся частью будущей миграции медиатеки.

Обычный путь не превращается в URI при хранении. Буквы дисков (`C:\`, `C:/`, `C://`) распознаются до URI-схемы; кириллица, `%` и `#` сохраняются. Маркер content URI — `content://` без учёта регистра схемы. Относительный файл вроде `content:local-song.mp3` остаётся файлом. Другие адреса с `scheme://`, включая HTTP и `file://`, не поддерживаются этой границей и не интерпретируются как локальные файлы. Внешний адаптер должен явно преобразовать file URI в файловый путь, если такая возможность понадобится.

Content URI проверяется на схему, непустую authority и путь; управляющие символы, неэкранированные пробелы и повреждённые `%`-последовательности отклоняются. Факт наличия провайдера/документа и разрешения это не подтверждает. Ошибки валидации не включают переданный адрес. При отсутствии названия UI показывает «Без названия» вместо непрозрачного ID провайдера.

Равенство ссылок определяется типом и исходной строкой. URI с разным регистром/кодированием остаются отдельными адресами: неоднозначное совпадение не объединяет записи. Сигнатура метаданных по-прежнему не уникальна. Только её запасной вариант без тегов для URI использует `uri:<исходная строка>` вместо файловой нормализации; прежние сигнатуры файлов не меняются. Полный SHA-256 файлов и правила точных копий не меняются.

## Проигрыватель

`LocalAudioEngine` принимает `setSource(AudioSourceReference, preload: ...)`. `JustAudioPlayerService` разбирает ссылку внутри контролируемой загрузки. Некорректный сохранённый адрес становится обычной ошибкой источника, без необработанного исключения или зависания в loading.

Для файлов сохраняются прежние абсолютный путь, File.exists, прямое открытие и Windows-повтор через защищённый кэш. Кэш дополнительно отклоняет URI до доступа к файлам и создания своих каталогов. Для content URI нет проверки File.exists, обращения к Windows-кэшу или файлового повтора при отказе доступа провайдера.

`JustAudioEngine` передаёт файл в прежний `just_audio.setFilePath`, а content URI — в `setAudioSource(ProgressiveAudioSource(uri))` только на Android. URI не превращается в file URI, и его окончание не выбирает HLS/DASH вместо обычного аудио. На desktop движок отклоняет content URI до native load. В движок передаётся объект Dart Uri через сериализацию установленного just_audio; сохранённая исходная строка при этом не перезаписывается. Проверка разрешений и реальные особенности провайдеров ещё требуют устройства.

Предзагрузка, два декодера, плавный переход, поколения отмены, история и очередь используют тот же общий механизм для обоих типов. Поздняя ошибка URI не подменяет новый трек, а отменённая фоновая подготовка не задерживает явный выбор другого источника. Отказ источника имеет прежний `PlayerFailureKind.source`, поэтому автоматический ограниченный обход недоступных кандидатов сохраняется.

## Проверки и следующий шаг

24 новых теста:

- 10 сценариев модели/Drift: совместимые пути, URI и кодирование, непрозрачные адреса, ошибочные значения без личных данных, typed-конструктор/правки/подписи, сигнатуры, сохранение в схеме 9, явная смена адреса с сохранением ID, лайка, статистики, истории и плейлиста.
- 11 сценариев проигрывателя: отсутствие файлового доступа/кэша, тихая подготовка, один audible start, crossfade/один completed, запоздалые ошибки, отмена standby без задержки явного выбора, отозванный доступ, повреждённый адрес, dispose, автоматическое восстановление, отказ кэша до IO и реальный локальный отчёт без URI/текста провайдера.
- 3 сценария каналов установленного just_audio 0.10.5: путь с Unicode/`%`/`#` становится file URI, Android-ветка передаёт content URI как progressive, desktop отказывает до загрузки. Android-ветка выбрана тестовым параметром на Windows; нативного Android-декодера и разрешений в этом тесте нет.

Android-проект/APK, SAF/MediaStore-обход, сохранение grants, URI-чтение метаданных/обложек/хэшей, смена разрешений и фоновый сервис пока не реализованы. Нынешний сканер остаётся файловым. Следующий технический прототип проверит эти границы на Xiaomi Redmi Note 14 Pro, 8/512 ГБ, Android 16. Поддержка адреса в модели сама по себе не даёт доступа к памяти телефона.

Обновление после пакетов 17–19: SAF отдельных файлов, постоянные grants,
нативные теги/миниатюры и фоновая медиаслужба реализованы. Пакет 18 подтверждён
на телефоне; фоновое поведение пакета 19 ожидает физической проверки.
MediaStore/массовые папки, URI-хэши и полный учёт/освобождение grants остаются
следующими задачами. См. [документный прототип](android-document-prototype.md)

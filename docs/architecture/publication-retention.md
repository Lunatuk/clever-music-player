**Пакет 36: журнал публикации, квоты и очистка**

Пакет 35 подтверждён пользователем. Новая часть относится к desktop download
coordinator; обычные запуск, воспроизведение и сканирование её не вызывают.
Схема БД остаётся 13, зависимости и поставляемый FFmpeg не меняются.

`DesktopPublicationStore.writeAudio` до создания `audio.part` записывает
неизменяемый `reservation.json`: ID задания/публикации, точный ключ, ожидаемый
размер и время. Ни путей, ни credentials в нём нет. Резерв учитывается целиком
даже при пустом/частично записанном файле. Общий OS `locks/quota.lock` защищает
проверку и резервирование для разных ресурсов и алиасов одной физической папки.
Он освобождается до потоковой записи/декодирования и не удерживает SQLite.
Прежний OS lock ресурса остаётся взят на всю публикацию.

По умолчанию разрешены 512 operation directories и 16 GiB суммарного staging.
Один файл по прежнему ограничен 8 GiB. Успешный `published.json` освобождает
байтовый резерв, когда `audio.part` уже отсутствует; готовая музыка не входит
в квоту. Legacy staging без reservation учитывается по фактическому размеру.
Количество operation directories учитывается до их удаления. Непонятное
содержимое блокирует новое резервирование; превышение квоты возвращает
`quotaExceeded`, coordinator сообщает `noSpace` без частичного импорта.
Содержимое входного stream при отказе admission не читается.

`PublicationRetentionPolicy` позволяет задать меньшие/большие лимиты в пределах
10 000 operations / 1 TiB и неотрицательные сроки. Это внутренний контракт,
пользовательских настроек квоты пока нет. Максимум 16 обычных файлов на operation,
16 KiB на обычный metadata record / 64 KiB на retirement record ограничивают
объём обхода. При превышении лимита данные не обрезаются и не удаляются.

`DesktopPublicationMaintenance.clean` явно получает папку и ID источника.
Coordinator вызывает её после первого heartbeat, перед открытием publisher.
Занятые ресурсы пропускаются. Ошибки отдельных удалений возвращаются в результате
и `cleanupFailed`; повреждённый корень журнала блокирует новую операцию.
После перехода на publication занятый quota lock переводит попытку в
needsReconciliation: recovery сначала возвращает её на download. Снимок с
неподходящим этапом не выдаётся как готовый к повторному processDownloadedFile.

Очистка проверяет owner.json, реальные типы каталогов/файлов без followLinks,
вычисленные имена и неизменяемые записи. Рекурсивного удаления нет. Для каждого
ресурса берётся прежний OS lock; lock files никогда не удаляются/заменяются.
Неизвестные имена, вложенные каталоги, ссылки и противоречивые записи сохраняются.
Пустой operation directory после удаления последнего marker может быть удалён
нерекурсивно: оставшихся данных для восстановления в нём нет.

Решение об удалении принимает `DriftPublicationRetentionRepository`:

| Состояние | Условие очистки служебных файлов |
| --- | --- |
| completed, final существует | Совпадают job ID/key, completed Track, folder/path, verified asset, publication ID/quality и доказательство байтов; полный SHA-256 final совпал под read seal |
| failed/cancelled, final отсутствует | Есть атрибуция intent/reservation; во всех поддерживаемых расширениях нет final; и запись, и завершение задания старше 24 часов |
| queued/running/needsReconciliation/reconciling | Сохранять, включая истёкший lease |
| Нет задания/asset/папки, папка отключена/перенесена | Сохранять |
| completed, final изменён/отсутствует; failed/cancelled с final | Сохранять |

По умолчанию importedAge равен нулю: подтверждённый импорт не должен заполнить
512 entries при первом обновлении большой коллекции. Последний журнал остаётся
до следующей coordinated operation или отдельного clean. Очистка не меняет
Track/asset/job/attempt/ref/history и никогда не удаляет итоговую музыку.
Активная авторизация для удаления уже подтверждённого частного журнала не нужна;
удалённая/отключённая папка всё равно сохраняет свои файлы.

Preflight БД отсекает незавершённые задания до дорогого хэширования. Затем
повторная transaction сначала выполняет writer reservation, снова проверяет
текущее состояние и разрешает короткий ограниченный файловый эффект. Смена
состояния/источника, произошедшая между проверками или пока transaction ждала
другого SQLite writer, не допускает удаления. Хэширование находится вне БД.
Для сохранившегося `audio.part` импортированной публикации требуется тот же
физический файл, что и final, например остаток POSIX link/unlink. Одного
совпадения хэша отдельной копии недостаточно.

До первого удаления атомарно сохраняется `retention.json` с исходными intent/
reservation. Он удаляется последним; затем удаляется пустой directory. Отмена,
ошибка доступа и закрытие процесса могут оставить частично очищенный operation.
Следующий clean восстанавливает атрибуцию из marker и снова проверяет БД/файлы.
Publisher pending/read/reconcile также понимают intent внутри retirement record,
если исходный intent.json уже исчез. Маркер сам по себе не разрешает удаление.
`close` отменяет и дренирует принятую работу; забытый Future наблюдается внутри.

Проверено 50 новыми тестами: 35 retention, 10 quota, два SQLite fences, три
coordinator regressions. Есть занятый OS resource lock и запрещённый Windows
delete, частичная очистка/отмена, повторное открытие persistent SQLite, чтение
recovery из retirement marker, конкурирующие резервирования до первого байта,
сохранение готовых песен/записей и освобождение квоты. Полный локальный набор:
1416 passed, concurrency 4, 58 секунд. В нём повторно исполнены четыре real
bundled-helper coordinator checks; analyze без замечаний.

Границы: это квота publication staging и ограниченный журнал. Входной скачанный
файл и отдельный `cmp_audio_metadata_*` workspace принадлежат вызывающему коду/
preparer и закрываются прежним механизмом. После аварийного завершения старые
неатрибутированные preparation directories не угадываются по имени; будущий
transport runner должен управлять их ownership и общим бюджетом raw/prepared
данных. Старый pre-intent staging без reservation также сохраняется. Сохранённые
неоднозначные данные могут занять квоту и потребовать явного разбора; достижения
лимита недостаточно для их удаления. Lock files и DB job/attempt history здесь
не очищаются. Native Windows/Mac locks не являются sandbox от посторонней
замены дерева; directory-fsync/power-loss гарантии не добавляются.

Яндекс adapter/credentials/«Мне нравится»/выбранные плейлисты/кнопка следуют далее.
macOS helper qualification и native Android SAF writer остаются отдельными
платформенными работами; desktop File API не используется для content URI.

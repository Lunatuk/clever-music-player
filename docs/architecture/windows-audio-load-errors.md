# Windows: ошибки открытия и фактическое состояние декодера

22 октября 2026: пользователь подтвердил, что с исправленной версией
воспроизведение на компьютере друга заработало. Ручная проверка доставки
пакета51 подтверждена; предыдущие записи об ожидании ниже — история диагностики.

Пакеты 50–51, 20 октября 2026 года. Android-пакет 49 ещё ожидает ручной проверки;
работа временно переключена на невоспроизведение файлов на другом Windows-PC.

## Уточнение по выпуску 50

Свежий отчёт друга содержит девять отказов открытия кэша с HRESULT
-2147024893 (0x80070003), включая только что созданные копии. Исходные файлы
читаются, копирование завершается, ошибка возникает при native open.

Проверка готового пакета выявила ошибку выпуска: DLL 50 собрана до изменения
DecodeFileUriUnicode. Повторная incremental-сборка завершилась успешно, но
не перекомпилировала native plugin после правки player.hpp/uri_utils.hpp.
В MSVC CL.read tlog этого проекта эти заголовки отсутствовали. Проверки
исходников и отдельного настоящего AudioPlayer прошли, однако они не доказали
состав упакованной DLL. Утверждение о наличии Unicode-исправления в ZIP 50
было неверным. Передача новых ошибок действительно присутствовала.

Пакет 51 заново собирает Windows из отдельной свежей копии. CMake следит за
шестью исходными файлами плагина, считает SHA-256 манифеста и включает digest
в compiler definitions. При пересчёте digest меняется команда компиляции.
DLL экспортирует CmpWindowsAudioBuildStamp — фиксированный stamp с этим hash,
без пользовательских данных. verify_windows_audio_plugin.py независимо
считает digest по исходникам и отвергает неподходящую/старую x64 DLL. Проверка
включена в Windows CI, обязательна перед native probe и выполняется после
сборки и распаковки выпуска. Временные метки не являются проверкой идентичности.

Android-код в 51 не меняется; новый пакет выпускается только для Windows.
Путь пользователя по-прежнему скрыт в отчёте, поэтому фактическое успешное
воспроизведение у друга должен подтвердить повтор одного трека.

## Что показали исходные отчёты

Получены три JSON-отчёта (два внутри ZIP) с перекрывающейся историей. Часть
открытий завершается и получает Play с volume/gain 1.0; другие останавливаются
после `cacheResolved`. В последнем отчёте с момента готовности кэша до экспорта
прошло около 25 секунд, но нет ни завершения открытия, ни ошибки.
Пользователь уточнил: не воспроизводятся все файлы, при этом эти файлы работают
в штатном Windows-проигрывателе и VLC на том же PC. Проблема не считается
подтверждённым системным mute или отсутствием кодеков.

Наличие движущейся позиции в UI не доказывает декодирование: и библиотека,
и наш Windows progress recovery могут вычислять время по часам.

## Воспроизведённая ошибка пути

Отдельный probe запускает настоящий production AudioPlayer/WinRT, а не mock:
из временных копий tone.mp3, tone.m4a и tone.flac. До исправления все три
играли из ASCII-папки, в том числе с пробелами, но те же байты из папки
«Музыка тест» возвращали HRESULT -2147024893 (0x80070003, путь не найден).
Передача того же file URI с буквальными Unicode-символами вместо UTF-8
percent sequences устранила отказ. Причина — представление пути на границе
Dart Uri.file → WinRT MediaSource::CreateFromUri. ASCII-имя кэш-файла не
помогает, если кириллица есть в пути профиля/каталога кэша.

DecodeFileUriUnicode перед созданием WinRT Uri декодирует только корректные
не-ASCII UTF-8 последовательности file: URI. ASCII escapes, включая %25,
%23, %3F, %2F, %5C и %20, сохраняются: имя файла с буквальным «%D0%90»
не превращается в другое имя. HTTP/HTTPS и другие схемы не преобразуются.
Невалидные, усечённые, overlong UTF-8, суррогаты и значения выше U+10FFFF
не декодируются. Преобразование идемпотентно. Сетевая загрузка/транскодирование
и изменение аудиофайлов не требуются.

Это подтверждённая ошибка нашего Windows-плагина. Исходные отчёты скрывают
пути и коды ошибок, поэтому нельзя утверждать, что причина у друга именно
такая же, до проверки пакета 50 на его компьютере.

## Подтверждённая несовместимость ошибок

Native `just_audio_windows` 0.2.3 отправлял `MediaFailed`/`ItemFailed` через
`EventSink::Error` с текстовым code. Установленный `just_audio` 0.10.5
игнорирует stream error envelopes и формирует errorStream из числовых
`errorCode/errorMessage` полей обычного playback event. Это изменение также
описано в локальном upstream CHANGELOG для 0.10.0.

Регрессия с настоящим установленным Dart SDK пакета и mock method/event
channels до изменения воспроизвела: native error отправлена, errorStream пуст,
setSource остаётся pending. Это доказывает потерю ошибок, но не устанавливает
исходный HRESULT на компьютере друга — старые отчёты его не содержат.

## Исправление

- Native asynchronous failures теперь публикуют обычный playback event с
  idle state и исходным signed HRESULT. При нулевом HRESULT используется
  E_FAIL. Сообщение фиксированное; произвольные строки Windows/URI не передаются.
- Синхронная ошибка CreateFromUri/load возвращается через MethodResult с
  числовым HRESULT. std::exception также получает фиксированный fallback.
- Windows engine подписывается на errorStream до setFilePath. Он сохраняет
  исходный PlayerException даже если библиотека завершает тот же load как
  PlayerInterruptedException после перехода в idle. Ошибка до первого Opening
  также завершает ожидание.
- Открытие ограничено 20 секундами на попытку. После ошибки/таймаута stop
  закрывает native platform; Dart-ожидание дренируется не дольше ещё 1 секунды,
  а поздний ответ остаётся с обработчиком ошибки. Потерянный старый method reply
  не удерживает новый декодер. Revision защищает stop/смену/закрытие.
- Прямой путь и Windows-кэш остаются прежними последовательными попытками;
  каждый отказ записывает audioLoadAttemptFailed с cached и HRESULT/типом.
  Финальный PlaybackLoadException сохраняет причину для отчёта; его текст
  остаётся общим. После отказа можно повторить запуск другого файла.

Лимит относится к native open, не к копированию файла. У прямой попытки и
попытки из кэша отдельный лимит: полное ожидание может составить около 42 секунд.
Это защита очереди от зависания, не обещание исправить любое внешнее состояние
Windows. Android/macOS не получают Windows timeout/race branch.

## Наблюдение без синтетических часов

Main method channel Windows-плагина предоставляет getPlaybackDiagnostics:
до восьми живых декодеров, без player ID, URI или имён. Для каждого читаются
реальные WinRT PlaybackSession.PlaybackState, Position, NaturalDuration и
наличие Source. State: None=0, Opening=1, Buffering=2, Playing=3, Paused=4.

Через три секунды после начала открытия/Play release-приложение делает один
снимок. Завершение открытия переносит таймер на Play. Отдельно записываются
текущая позиция UI и native позиции, opening и число/слоты декодеров. Слоты —
все живые native players, включая подготовленный второй deck; это не
утверждение, что каждый слот воспроизводит выбранный trackId.

Пустой список фиксируется явно. Чтение ограничено двумя секундами; его ошибка
не останавливает музыку. Timer отменяется при закрытии; принятая операция
дренируется, запоздалый снимок другой сессии не записывается. В отчёт попадают
только числовые/boolean поля. Схема БД и зависимости не меняются.

## Проверки и пределы вывода

C++ fixture строит те же settings/error/snapshot payloads, что native plugin;
MSVC-команда сравнивает все три с JSON, используемыми Dart-тестами. Проверяются
ранняя/поздняя/synchronous native ошибки, lazy preload, потерянный method reply,
timeout/stop/retry, смена выбранного трека при pending native open, runtime
errorStream, сохранение HRESULT и timeout через кэш, privacy и snapshots.

Полный native плагин компилируется в Windows release. Тесты method channels
не подменяют физическую проверку на проблемном компьютере. Требуется один
запуск выбранного файла и свежий отчёт: по нему можно определить фактический
Native state/позицию и исходный код отказа. Успех на PC друга пока не заявляется.

Дополнительно прошли 32 standalone C++ URI-регрессии и 26 проверок с реальным
WinRT: 24 воспроизведения (3 формата × ASCII/пробелы/кириллица/emoji/# и %/
буквальные percent sequences/CJK/комбинируемые знаки) и два повреждённых файла.
Для успеха требуется движение именно WinRT Position при Playing; UI-часов
в probe нет. Повреждённый файл должен вернуть обычный event с HRESULT,
без старого EventChannel error envelope. Аудио probe отключено через Volume(0).
Используются только свежие временные копии синтетических fixtures, без
пользовательской музыки, SQLite, API или учётных данных.

Повторение после Windows release-сборки (нужны MSVC, Windows SDK и Python):

```powershell
.\tool\check_windows_audio_contract.ps1 -FlutterRoot 'C:\Flutter SDK\flutter' `
  -NativeReleaseDirectory 'C:\build\clever-music-player\build\windows\x64\runner\Release'
```

Без NativeReleaseDirectory выполняются три проверки protocol fixtures и
32 URI-регрессии. Результаты реального декодирования сохраняются в
.dart_tool/windows-audio-contract/native_playback_results.json.
